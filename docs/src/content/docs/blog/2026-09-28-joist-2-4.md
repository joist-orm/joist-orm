Joist [2.4](https://github.com/joist-orm/joist-orm/commit/5dc88892e78974b3441ee38b78bf314c4a4f7a29) is out!

The big addition is that Joist _finally_ 😅 supports arbitrary low-level SQL statements with `em.query` for `SELECT`s and `em.execute` for `INSERT`s, `UPDATE`s, and `DELETE`s.

## `em.query`: When `em.find` Isn't Enough

For most application code, Joist's `em.find` and entity mutations have been, and continue to be the right tools are still the right tools. But there has always been a small set of queries that need a `GROUP BY`, a custom projection, or a subquery. Until now, those meant dropping down to another query builder or writing SQL ourselves. Joist 2.4 gives those queries a home alongside the rest of the ORM.

`em.find` is deliberately focused on loading entities. That focus lets Joist automatically batch finds, which is a big part of how we avoid N+1s. It also means `em.find` doesn't try to be a general-purpose SQL builder: it doesn't return arbitrary rows from a grouped query, for example.

Say we want the ten authors with the most books, including a book count. We can now write:

```ts
import { tables } from "joist-orm";

const [a, b] = tables(Author, Book);
const rows = await em.query({
  select: { name: a.firstName, bookCount: b.id.count() },
  from: a,
  join: [a.books.as(b)],
  groupBy: [a.id, a.firstName],
  orderBy: { bookCount: "DESC" },
  limit: 10,
});
// rows: { name: string; bookCount: number }[]
```

The interesting part is that the result type follows the `select`: we asked for `name` and `bookCount`, so that's what we get back. The tables and columns are typed from the generated entities, and Joist converts values such as tagged ids and enums back into their domain types.

The API is a plain object literal, rather than a chain of `.select().from().join()` calls. This is admittedly a matter of taste, but JavaScript is quite good at building objects, and we've found the same approach works well for `em.find`'s dynamic filters. `em.query` carries that idea down to SQL-level queries: optional conditions (and joins that are no longer needed) can be pruned, instead of making you assemble the query imperatively.

You can also select an entity rather than a custom row. In that case Joist loads it through the identity map, and you can request populated relations, much like `em.find`. For queries that need more SQL, there's support for aggregates, subqueries, `EXISTS`, CTEs (including recursive CTEs), set operations like `UNION`, and typed SQL expressions. The [SQL Queries docs](/features/queries-raw/) have the examples and full API details.

One important tradeoff: **`em.query` is not auto-batched.** Every call issues a database query, including calls made inside a loop. Use `em.find` for ordinary entity loading, especially in nested resolvers; reach for `em.query` when you need control over the SQL or the returned shape.

## `em.execute`: Immediate SQL Writes

The companion API, `em.execute`, handles SQL mutations. For example, a bulk update can use the same typed table and column expressions:

```ts
import { table } from "joist-orm";

const b = table(Book);
const result = await em.execute({
  update: b,
  set: { title: "Revised title" },
  where: b.title.eq("Draft title"),
  returning: b.id,
});
// result.rows: BookId[]
```

There are also `insert` and `delete` forms, with typed `returning` results. This is useful when the job really is a set-based SQL operation rather than a collection of entity edits; see the [SQL Mutations docs](/features/sql-mutations/) for those forms.

The boundary here matters: `em.execute` issues SQL immediately. It does **not** flush pending entity changes or run Joist's entity hooks, validation, reactive fields, defaults, or optimistic locking for those writes. If you already have affected entities loaded, their in-memory state may also be stale. For normal domain-model changes, keep mutating entities and calling `em.flush()`; use `em.execute` when you intentionally want the lower-level operation.

## Also in 2.4

A few other additions worth mentioning:

- **Commit rules** ([#1927](https://github.com/joist-orm/joist-orm/pull/1927)) run validation after SQL has been flushed but before the transaction commits. This lets a rule query the *new* database state and still roll back the transaction if validation fails. See the [validation rules docs](/modeling/validation-rules/#commit-rules).
- **Configurable tagged-id delimiters** ([#1931](https://github.com/joist-orm/joist-orm/pull/1931), [#1932](https://github.com/joist-orm/joist-orm/pull/1932)) allow URL-friendly ids without the usual `:`, or a different delimiter if that better fits your application. See [Tagged IDs](/advanced/tagged-ids/).
- **Dual CommonJS/ESM packages** ([#1972](https://github.com/joist-orm/joist-orm/pull/1972)) make Joist usable from both module systems.

There are also fixes across soft deletes, relation loading, reactivity, and GraphQL resolvers. The [2.4 changelog](https://github.com/joist-orm/joist-orm/releases/tag/v2.4.0) has the full list.

For us, the important shift is that `em.find` can stay focused on the common, N+1-safe entity-loading path, without making the SQL-shaped cases feel like an escape hatch to an entirely different API. We're excited to see what people build with it! 🎉
